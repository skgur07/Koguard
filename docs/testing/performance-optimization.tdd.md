# 정규화·공백 매칭 성능 최적화 TDD 증거

## 사용자 여정

채팅 서버에 인라인으로 붙이는 사용자는 최대 입력 길이에서도 요청 지연이 눈에 띄지 않아야
한다. 이전 기준선의 최대 입력 4096자 p95는 5.59ms, 적대 입력은 99.03ms였다. 계획 §8.3의
최대 입력 p95 15ms 게이트에 여유가 크지 않았다.

## 범위

동작을 바꾸지 않는 최적화만 수행한다. 탐지 결과, 매치 순서, 원문 span은 모두 그대로여야
한다. 사전이나 matcher 기본값 변경은 이 작업에 포함하지 않는다.

## 측정으로 찾은 병목

`cProfile`로 두 대표 입력을 프로파일했다.

| 입력 | 병목 | 비중 |
| --- | --- | --- |
| 적대 입력 (`"a "` × 2048, 사전 256개) | `matcher._find_longest_whitespace_gap_occurrence` | tottime의 72% |
| 실사용 4096자 한국어 | `normalizer._is_unicode_cluster_extension` | cumtime의 약 28% |

첫 번째 함수는 `while cursor < len(normalized.text)` 형태로 루프마다 `len()`을 호출했고,
`normalized.text` 속성도 반복당 세 번 조회했다. 호출당 `len()`이 약 100만 회였다. 또한
`boundaries.starts[start]`는 루프 안에서 값이 바뀌지 않는데 매 반복 검사하고 있었다.

두 번째 함수는 문자 하나에만 의존하는 순수 함수인데 매 문자마다 `unicodedata.category`를
호출했다. 검사당 14,040회였다.

## 적용한 변경

### 1. 루프 불변식 호이스팅 (`matcher.py`)

- `normalized.text`와 그 길이를 루프 밖으로 꺼냈다.
- `boundaries.ends`를 지역 변수로 묶었다.
- `boundaries.starts[start]`가 거짓이면 trie를 걷기 전에 `None`을 반환한다. `start`는 루프
  안에서 변하지 않으므로 이 경우 후보가 만들어질 수 없다.

### 2. 코드 포인트 fast path (`normalizer/__init__.py`)

U+0300 미만과 한글 음절 영역(U+AC00–U+D7A3)에는 결합 문자도 변이 선택자도 없다. 이 두
구간은 표를 찾지 않고 범위 비교로 답한다. 나머지 코드 포인트만 `lru_cache(maxsize=1024)`가
붙은 조회 함수로 넘긴다.

AGENTS.md는 캐시 추가 시 정확성, 메모리 상한, 동시성 정책을 먼저 정의하도록 요구한다.

- 정확성: 코드 포인트 하나의 순수 함수다. `unicodedata.category`는 해당 Python 빌드에서
  고정된 표를 읽으므로 캐시된 값이 낡을 수 없다.
- 메모리 상한: 1024개 항목, 각 항목은 1문자 키와 bool이다.
- 동시성: `lru_cache`가 자체 장부를 직렬화하며, 함수가 순수하므로 동시 miss가 같은 값을
  중복 계산할 뿐 결과가 달라지지 않는다.

## 검증

동작 변경이 아니므로 실패하는 테스트를 먼저 만들지 않았다. 대신 변경 전에 참조 구현과의
동치를 고정하는 오라클 테스트를 추가했다.

- 새 테스트: `tests/test_normalizer_fast_paths.py`
  - U+0000–U+10FFF 전 구간에서 fast path와 참조 구현의 결과가 일치한다
  - 변이 선택자 보충 영역 U+E0000–U+E01FF에서도 일치한다
  - 건너뛰는 두 구간에 결합 문자가 존재하지 않음을 Unicode 표로 직접 확인한다
- 기존 436개 테스트 전부 통과, branch coverage 95.64%
- `evaluation/corpus` 166개 케이스 결과가 최적화 전후 완전히 동일

## 하지 않은 것

적대 입력은 여전히 p95 71.9ms로 계획 §8.3의 15ms를 넘는다. 남은 비용은 trie 순회 자체이며
스텝당 `dict.get` 한 번까지 줄어 있다. 더 줄이려면 공백 매칭 알고리즘을 바꿔야 하는데, 이
입력은 사전 256개 항목이 전부 서로의 접두사이고 입력이 한 글자의 반복인 합성 사례다. 실사용
경로의 정확성을 걸 만한 거래가 아니라고 판단해 중단했다. 계획 §8.3의 적대 입력 조건인
"설정된 계산량·입력 길이 상한 안에서 종료"는 충족한다.
