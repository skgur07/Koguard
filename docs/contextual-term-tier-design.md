# 문맥 의존 term tier와 profile 설계 (층 3)

- 작성일: 2026-09-04
- 상태: **설계만 확정, 구현 보류**
- 선행 문서: [제품 집중 계획](product-focus-plan.md) §7, [정확도 기준선](accuracy-baseline.md)

## 요약

일부 금칙어는 정상 국어 용법과 형태가 완전히 같아 어떤 규칙으로도 구분할 수 없다. 이런
항목을 기본 사전에서 분리하고, `profile` 하나로 사전 tier와 matcher 집합을 함께 고르게
하는 설계다.

**지금 구현하지 않는다.** 현재 기본값 대비 이득이 문장 F1 +0.011로 작고, 독립 문장 세트에서는
차이가 0이다. 이 설계의 값은 사전 확장 시점에 나타난다. 아래 §7에 근거를 수치로 남긴다.

## 1. 문제

다의어 오탐은 발생 위치에 따라 세 부류로 나뉘며, 앞의 둘만 규칙으로 해결된다.

| 부류 | 예 | 정상 용법 | 해결 |
| --- | --- | --- | --- |
| 어절 안 충돌 | `등신`대, `새끼`발가락 | 복합명사 | 층 1: 조사 규칙과 term별 매칭 모드 |
| 어절 밖 충돌 | `꺼져` 있다, `닥쳐`올 | 보조용언·연결어미 | 층 2: Whitelist 구. **적용 완료** |
| 형태 완전 동일 | `보지` 못했어, `걸레`로 | 같은 표기, 같은 조사 | **층 3: tier 분리** |

세 번째 부류는 형태소에 아무 신호가 없다. `걸레`(청소도구)와 `걸레`(비하)는 같은 단어이고
같은 조사를 받는다. 구분하려면 문맥 이해가 필요하고, 그것은 규칙 기반 substring 매칭의
범위 밖이다.

## 2. 데이터 설계

```
src/koguard/data/
  badwords.txt              core tier
  badwords-contextual.txt   contextual tier
```

### 편입 기준

> 정상 국어 용법이 존재하고, **그 용법의 보어 집합이 열려 있어** 층 2 Whitelist로 열거할 수
> 없는 표현.

기준으로 판정한 결과다. corpus 수치에 맞춘 선별이 아니다.

| term | 정상 용법 | 보어 집합 | tier |
| --- | --- | --- | --- |
| `꺼져` | 꺼져 + 임의 용언 (어두워졌다, 조용해졌다) | 열림 | contextual |
| `뒤질` | 뒤질 + 임의 명사 (각오, 기세, 결심) | 열림 | contextual |
| `닥쳐` | 닥쳐올, 닥쳐온, 닥쳐서 | 닫힘 | core (층 2가 처리) |
| `등신` | 등신대, 등신불 | 닫힘 | core (층 2가 처리) |

기준 없이 다의어 5개를 모두 옮기면 문장 F1이 0.9000으로 떨어진다. 기준대로 2개만 옮기면
0.9268이다.

### 왜 컬럼이 아니라 별도 파일인가

tier는 항목 수가 적고 한눈에 보여야 하며, 출처 고지를 파일 단위로 유지할 수 있다. 층 1의
매칭 모드는 항목마다 달라 컬럼이 맞다. 두 축은 공존한다. tier는 파일, 모드는 컬럼이다.

## 3. API 설계

```python
KoguardEngine()                        # profile="balanced" 와 같다
KoguardEngine(profile="strict")
KoguardEngine(profile="aggressive")
```

계약:

- `profile`과 `config`를 동시에 전달하면 `ConfigurationError`를 던진다. 정책 출처가 둘이
  되는 것을 막는다. 계획 §7.3의 요구다.
- 명시적 `dictionary=`는 profile이 고른 사전을 덮어쓰되, matcher 설정은 profile을 따른다.
- resolved config는 `engine.config`에서 확인할 수 있다.
- **`Match`에 tier를 노출하지 않는다.** 계획 §5.2는 카테고리를 공개 필드로 바로 추가하지
  말고 build/evaluation metadata로만 관리하도록 정한다.

## 4. profile 정의

| | strict | **balanced** | aggressive |
| --- | :---: | :---: | :---: |
| core 사전 | O | O | O |
| contextual 사전 | X | X | **O** |
| exact, alias | O | O | O |
| repeated, separator, whitespace, mixed, keyboard, jamo, 초성, segmented | X | O | O |
| fuzzy | X | X | O |

측정값이다. 166개 evaluation corpus 기준이며 지연은 기본 사전, 4096자 한국어 입력이다.

| profile | precision | recall | F1 | 정상 문장 FP | 짧은 입력 | 4096자 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| strict | 0.9333 | 0.6667 | 0.7778 | 0.00% | 0.028 ms | 3.14 ms |
| balanced | 0.9500 | 0.9048 | 0.9268 | 0.00% | 0.057 ms | 6.64 ms |
| aggressive | 0.8478 | 0.9286 | 0.8864 | 4.10% | 0.088 ms | 10.20 ms |

## 5. 계획 §7.2와 달라지는 두 가지

### strict는 정밀도 profile이 아니라 지연 profile이다

계획은 strict를 오탐 최소 구성으로 상정했다. 측정하면 우회 탐지 단계는 오탐을 만들지 않으며
(ablation dFP +0), strict의 정상 문장 FP도 balanced와 같은 0.00%다. 실제 차이는 지연 2배와
재현율 급락뿐이다. 따라서 strict는 "정밀도가 필요한 서비스"가 아니라 "지연이 극도로 중요한
경로"용으로 문서화해야 한다. 이름이 오해를 부르면 `minimal`이 낫다.

### 초성과 segmented는 balanced에 포함해야 한다

계획 §7.2는 둘을 balanced에서 제외했다. ablation은 각각 dTP -2, -1이고 dFP는 0이다. 제외할
근거가 없다.

## 6. 테스트 계약

- profile별 `EngineConfig` 전 필드를 명시해 단언한다. 새 matcher가 실수로 기본 활성화되지
  않게 하려는 계획 §7.3의 요구다.
- `profile`과 `config` 동시 전달 시 `ConfigurationError`.
- `KoguardEngine()`과 `KoguardEngine(profile="balanced")`가 같은 결과를 낸다.
- contextual 항목이 balanced에서 미탐지, aggressive에서 탐지된다.
- profile별 정확도 예산. balanced는 정상 문장 오탐 0건, occurrence recall 0.88 이상.

## 7. 지금 구현하지 않는 이유

### 단독 이득이 작다

| | 문장 F1 | 정상 FP | 4096자 |
| --- | ---: | ---: | ---: |
| 현재 기본값 | 0.9630 | 1.64% | 6.69 ms |
| 층 3 balanced | 0.9744 | 0.00% | 6.52 ms |

문장 F1 +0.011이다. 이 corpus 밖의 독립 25문장 세트에서는 `꺼져`와 `뒤질`이 나오지 않아
차이가 정확히 0이다. 지연도 사전 2개 차이라 노이즈 수준이다. `strict`가 2배 빠른 선택지를
추가하지만 기존 경로를 빠르게 만들지는 않는다.

### 사전 확장 시점에는 필수가 된다

MIT Korcen에서 선별한 813개를 더해 871개로 확장하고 측정했다.

| | 문장 F1 | 정상 문장 FP |
| --- | ---: | ---: |
| 확장, tier 없음 | 0.7723 | **18.03%** |
| 확장 + 층 3 tier | 0.8764 | 8.20% |

tier 없이 확장하면 정상 문장 다섯 개 중 하나를 잘못 잡는다. 즉 층 3은 현재 성능을 올리는
기능이 아니라 **사전 확장의 전제조건**이다.

### 오탐 원인이 좁다

871개 중 정상 문장을 때린 항목은 8개뿐이었다.

```
보지 8건 · 자지 4건 · 새끼 4건 · 섹스 2건 · 세끼 1건 · 꺼져 1건 · 뒤질 1건 · sex 1건
```

전부 형태 완전 동일 부류다. 규칙으로 가릴 수 없고 tier로만 다룰 수 있다.

### 8.20%도 아직 게이트 밖이다

유죄 8개를 빼도 8.20%가 남는다. 뺀 항목이 사라지자 다른 항목이 대신 매치되는 두더지잡기가
시작된다. **확장 사전을 통째로 투입하는 접근은 실패한다.** 계획 §5.4가 후보마다 positive
1개와 hard negative 2개, matcher별 증분 측정을 요구하는 이유가 이 수치로 확인된다.

## 8. 이 설계가 하지 않는 것

- **심각도 축을 만들지 않는다.** 지금 필요한 축은 "얼마나 심한가"가 아니라 "얼마나
  모호한가"다. 둘을 섞으면 `보지`(심함이면서 모호함)를 분류할 수 없다.
- 성적, 정치, 인종 같은 정책 카테고리를 도입하지 않는다. 계획 §2의 비목표다.
- tier를 3단계 이상으로 나누지 않는다. 현재 데이터로 정당화할 수 없다. 다만 사전 확장 때
  `보지`, `자지`, `새끼`처럼 aggressive에서도 위험한 항목이 확인되면 `opt_in_only` 3단계가
  필요할 수 있다. 그때 측정하고 정한다.

## 9. 재개 조건

다음 중 하나를 만족할 때 구현한다.

1. 사전 확장 배치에서 형태 완전 동일 부류(`보지`, `자지`, `새끼` 등)를 처음 승격하려 할 때
2. 단순 진입 API(`profile`, `contains()`) 작업을 시작할 때. 계획 Workstream C와 함께 하면
   공개 표면을 한 번만 바꾼다
3. 서비스에서 `꺼져`, `뒤질` 오탐이 실제로 보고될 때

## 10. 재현 방법

```powershell
uv run python -m evaluation.koguard_runner --split all --ablation
```

이 문서의 수치는 `evaluation/corpus`의 166개 케이스(hard negative 122, positive 40,
review 4)에서 나왔다. corpus 규모가 계획 §6.7 목표에 못 미치므로 구현 간 상대 비교와 회귀
감지 용도로만 쓴다.
