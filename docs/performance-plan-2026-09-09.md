# Koguard 실시간 처리 성능 개선 기획

- 작성일: 2026-09-09
- 기준 commit: `e6576925cfce46ed0c23356d4610be3a5b0cebbe`
- 상태: **구현 제안**. 제품 코드, 기본 profile, 기존 API 계약과 출시 현황판은 변경하지 않았다.
- 목적: 채팅·댓글에서 bool 판정을 낮은 지연으로 제공하면서 원문 구간을 반환하는 상세 API도 유지한다.
- 근거: [Korcen 실측 비교](comparisons/korcen-2026-09-09/README.md), 이번 추가 프로파일링·Fuzzy 제외 실험.

## 1. 권장 방향

**일반 입력의 정규화를 가볍게 만들고, `contains()`를 실제 bool 판정에 맞게 최적화한다.**
`check()`는 다중 탐지·원문 위치·방법을 제공하는 상세 API로 유지한다. 탐지 범위는 기존
profile과 사용자 설정으로 제어하고, 반환 정보의 양 때문에 발생하는 비용을 별도로 줄인다.

단기 사용 절충안은 **aggressive에서 Fuzzy만 끈 구성**이다. 이번 진단에서는 상당수 우회 기능을
유지하면서 약 30% 비용을 줄였다. 다만 이것만으로 Korcen의 빠른 양성 반환과 동급이 되지는 않는다.
기본 balanced를 즉시 바꾸거나 새 profile 이름을 추가하지 않고, 기존 설정으로 제공할 수 있다.

기획에서 유지할 제품 가치는 세 가지다.

1. 기본 탐지 여부를 짧고 빠르게 확인하는 호출.
2. 서비스별 사전·Whitelist와 명시적인 탐지 범위.
3. 필요할 때 모든 매치와 정확한 원문 위치를 얻는 상세 호출.

## 2. 속도 차이를 어떻게 해석할 것인가

동일 Windows/CPython 3.11.9 비교의 p95 중앙값이며 단위는 ms다.

| 입력 | balanced | aggressive | Korcen 1.0.3 |
| --- | ---: | ---: | ---: |
| 짧은 정상 채팅 | 0.0262 | 0.0955 | 0.0435 |
| 짧은 욕설 문장 | 0.0437 | 0.0917 | 0.0068 |
| 정상 패턴 4,096자 | 4.5166 | 7.0015 | 5.2763 |
| 마지막에 욕설이 있는 4,096자 | 4.3971 | 10.3717 | 1.7762 |

짧은 욕설에서는 balanced가 약 6.4배 느리지만 절대 차이는 약 0.037ms다. 긴 양성 입력에서도
차이가 있고, 정상 입력에서는 balanced가 Korcen보다 빠른 사례도 있다. 따라서 “모든 입력에서
몇 배 느리다”는 결론 대신 **양성 입력의 비용을 줄이면서 정상 입력의 비용을 유지**하는 목표가 맞다.
이 절대 지연 차이가 중요한지는 실제 요청량과 서비스의 CPU·응답시간 예산으로 판단해야 한다.

평가에는 정상·직접 욕설·우회 입력, 욕설 위치가 앞/중간/끝인 경우를 모두 포함한다.
실제 분포가 없을 때는 정상 비중 50%/90%/99%의 가상 workload를 각각 측정하고 가정임을 표시한다.
그룹별 p95를 가중 평균해 전체 p95로 쓰지 않고, 섞인 호출 스트림의 지연을 직접 기록한다.

## 3. 추가 조사에서 확인한 병목

기준 소스의 엔진을 재사용하여 짧은 입력은 1,000회, 긴 입력은 40회 `contains()`에 대해
`cProfile`로 호출 비용을 조사했다. 아래는 **프로파일러가 관측한 누적 시간 비중**이다.
자식 함수 시간이 포함되어 서로 중첩되므로 항목을 더하면 안 된다.

| profile·입력 | 주요 관측 |
| --- | --- |
| balanced·짧은 정상 | `normalize_text` 약 61.5% |
| balanced·짧은 욕설 | `normalize_text` 약 46.5%, Exact 탐지 약 24.8% |
| balanced·4,096자 정상 | `normalize_text` 약 78.8% |
| balanced·4,096자 끝 욕설 | `normalize_text` 약 78.1% |
| aggressive·짧은 정상 | Fuzzy `find` 약 32.8%, 정규화 약 24.1%, 공백 탐지 약 19.6% |
| aggressive·4,096자 끝 욕설 | 정규화 약 41.4%, 공백 탐지 약 24.4%, Fuzzy 약 19.5% |

원본은 [프로파일 결과](performance-plan-2026-09-09.profile.json)에 있다.
프로파일러는 Python 호출에 오버헤드를 더하므로 이 비중을 실제 wall-clock 개선율로 환산하지 않는다.
Python 공식 문서도 [profiling과 benchmarking의 용도를 구분](https://docs.python.org/3.11/library/profile.html)한다.

코드상 원인은 다음과 같다.

- [engine.py](../src/koguard/engine/engine.py)의 `contains()`는 `check()` 전체를 실행한다.
  정상화·보호 구간·전체 탐지·우선순위 정리·결과 객체를 생성한 뒤 bool만 남긴다.
- [normalizer](../src/koguard/engine/normalizer/__init__.py)의 `normalize_text()`는 이미 정규화가
  불필요한 일반 한글에서도 글자별 검사와 원문 위치 tuple 생성을 수행한다.
- 고급 profile은 결과가 이미 있어도 나머지 활성 단계를 처리한다. 단순히 `Match` 생성을
  생략하는 것만으로 정규화·전체 검색 비용까지 사라지지는 않는다.

따라서 결과 객체 생성 최적화만으로 6배 차이를 해소한다고 약속할 수 없다.

## 4. 단기 절충안: Fuzzy만 선택적으로 끄기

현재 API로 사용할 수 있는 구성이다. 실제 기본값을 바꾸는 작업은 아니다.

```python
from dataclasses import replace
from koguard import KoguardEngine

config = replace(
    KoguardEngine(profile="aggressive").config,
    fuzzy_matching=False,
)
engine = KoguardEngine(config=config)  # 생성한 엔진을 여러 요청에서 재사용
detected = engine.contains("검사할 문장")
```

같은 입력을 10회 warmup, 100회 측정, 대상 순서를 교대한 3라운드로 추가 비교했다.
아래는 라운드별 p95의 중앙값이다. 앞 절의 독립 프로세스 비교와 실행 방식이 다르므로,
**이 표 안의 두 구성 사이에서만** 개선율을 계산한다.

| 입력 | aggressive | Fuzzy 제외 | 감소 |
| --- | ---: | ---: | ---: |
| 짧은 정상 | 0.0791ms | 0.0539ms | 약 32% |
| 짧은 욕설 | 0.0784ms | 0.0547ms | 약 30% |
| 4,096자 정상 | 6.8202ms | 4.6681ms | 약 32% |
| 4,096자 끝 욕설 | 9.6072ms | 8.0000ms | 약 17% |

직접 표현 12건의 탐지는 10건으로 동일했고, 정상 진단 20건의 오탐도 0으로 동일했다.
우회 12건의 탐지는 **11→10건**이 되었으며 차이는 `개세끼` 한 건이었다.
표본은 구현 유래 진단으로 편향되어 있다. 다른 오타까지 같은 비용·미탐 교환을 보장하지 않는다.
원본은 [Fuzzy 제외 실험](performance-plan-2026-09-09.fuzzy-ablation.json)에 기록했다.

이 구성은 공백·구분자·자판·자모 우회가 필요한 실시간 서비스의 선택지다.
기본 balanced는 계속 최소한의 승인된 matcher를 제공하고, 오타 탐지가 필요한 사용자는
aggressive를 선택한다. “실시간”이라는 새 공개 profile 이름은 독립 평가 근거가 생긴 뒤 결정한다.

## 5. 구현 제안

### A. 일반 문장의 정규화 비용 낮추기 — 최우선

문자열 전체가 현재 정규화 정책상 그대로 유지된다는 것을 저렴하게 확인할 수 있는 입력에
한해 빠른 경로를 사용한다. 우선 완성형 한글·허용된 ASCII·단일 공백처럼 좁은 범위에서 시작한다.
탭·연속 공백·분리 자모·결합 문자·format 문자 등은 기존 정규화로 보낸다.

`unicodedata.is_normalized()`만으로 Koguard의 whitespace·format 제거까지 같다고 판단하면 안 된다.
Unicode 정규화와 프로젝트 자체 변환은 다른 조건이다.
[Python Unicode API](https://docs.python.org/3.11/library/unicodedata.html)는 전자의 확인에만 사용한다.

`normalize_text()`에는 이미 **글자별** 빠른 경로가 있다. `_is_stable_character()`로 걸러
`unicodedata.normalize` 호출을 건너뛰는 분기이며 `110faa3`에서 보강했다. 따라서 여기서
제안하는 것은 그 분기의 추가가 아니라 **문자열 전체를 한 번에 통과시키는 경로**이고,
남은 비용도 `unicodedata` 호출이 아니라 Python 글자 루프와 tuple 할당이다.
4,096자 일반 한글에서 `normalize_text` 3.12ms 중 약 2.68ms가 루프 본문이고
글자별 span tuple 생성이 약 0.44ms다.

원문과 정규화문이 같은 경로에서는 인덱스가 같다는 사실을 내부적으로 표현하고,
불필요한 글자별 `(start, end)` 객체를 줄이는 방안을 측정한다. `source_spans`와
`original_span`을 직접 읽는 지점은 현재 **62곳**이다(normalizer 55, matcher 7).
이 규모 때문에 span 표현 변경은 선택적 후속이 아니라 P1의 필수 범위로 다룬다.
근거는 아래 7절의 목표 재산정에 있다. 필요 시 기존 mapping으로 전환하는 경계도 함께 설계한다.
외부로 반환하는 원문 span, Whitelist 겹침, 정규화문은 현재 결과와 같아야 한다.

**완료 조건:** NFC/NFKC·한글 조합·제로폭/결합 문자·연속 공백의 결과와 span 회귀가 없고,
긴 정상 입력의 실제 p95가 개선된다. 빠른 경로 밖 입력은 기존 경로와 같은 결과를 반환한다.

### B. `contains()`의 전용 bool 경로 — A와 함께 핵심 작업

일반형 경로에서는 전체 `Match` 목록과 `CheckResult`를 만들지 않고, Whitelist에 보호되지 않는
유효 후보가 존재하는지를 검사한다. 먼저 **Fuzzy가 꺼지고 변환 view가 단순한 strict/balanced**를
최적화한다. 처리 가능성을 증명하지 못한 설정은 기존 `check().detected`로 되돌린다.

유지할 계약:

- 정상 반환 시 `contains(text) == check(text).detected`.
- 잘못된 타입, 입력 길이, 공개된 계산량 제한 예외를 그대로 유지.
- 사용자 사전·Alias와 Whitelist, 동시 호출 동작 유지.
- `check()`의 다중 match·순서·원문 span·점수와 탐지 범위 유지.

현재 [contains 계약](contains-api.md)과 `tests/test_contains.py`는 **`check()`를 정확히 한 번
호출한다는 구현까지 보장**한다. 내부 최적화 전에 이 부분을 “결과·예외의 동등성” 계약으로
수정하기로 명시적으로 결정해야 한다. 위임 횟수 테스트는 광범위한 동등성 테스트로 대체하며
기능 검증을 약화하지 않는다. `check()` 재정의에 의존하는 서브클래스는 기존 위임으로 fallback하거나
지원 범위를 명확히 정한다. 이 문서 자체는 그 계약 변경을 실행하지 않는다.

### 조기 반환이 안전하지 않은 두 사례

두 사례 모두 현재 소스에서 직접 재현했다.

1. **변환 view의 Whitelist:** 사용자 blacklist `tlqkf`, whitelist `시발`, aggressive에서
   `check("tlqkf").detected`는 False다. 원문에는 금칙어가 있어도 자판 변환 view의 Whitelist가
   같은 원문 구간을 보호한다. 원문 Exact를 찾자마자 True를 반환하면 틀린다.
2. **후속 Fuzzy 예외:** `EngineConfig(fuzzy_max_operations=1)`로 `contains("병신 abcdef")`를
   호출하면 `FuzzyOperationLimitError`가 발생한다. 앞에서 Exact가 보인다는 이유로 True를
   반환하면 문서화한 예외 동등성이 깨진다.

따라서 고급 view에서 보호될 가능성이 있는 후보는 필요한 보호 검사를 끝내기 전에 반환하지 않는다.
Fuzzy 활성 설정은 우선 기존 전체 경로를 유지한다. 계산을 덜 하는 것과 현재 공개된 예외를
조용히 숨기는 것을 구분한다. 일반형에서 시작해 증명된 설정만 빠른 경로로 확대한다.

### C. 검색·변환 전 작업을 보수적으로 줄이기

A/B 이후 남은 비용에만 적용한다.

- 입력의 문자 종류·공백·구분자 정보를 한 번 조사해 공유한다. 같은 view와 같은 보호 mask를
  반복 계산하거나 합치지 않도록 한다.
- 초성·자판·자모 처리의 생략 조건은 설정과 입력 특성으로 증명한다. 사용자 사전의 로마자
  항목과 Unicode 정규화 후 생기는 후보도 고려한다.
- 작은 literal 사전에서는 Python automaton과 `str.find`, escape한 고정 regex 후보 검색을
  비교한다. 사전 67/1,000/10,000개와 공통 접두사·중복 후보로 측정해 선택한다.
  [고정 regex](https://docs.python.org/3.11/library/re.html)는 엔진 생성 시 준비하고 사용자 사전 항목을
  regex 코드로 취급하지 않는다.

빠른 후보 검사는 false positive를 허용하더라도 **기존 탐지를 놓치면 안 된다.** 후보가 없어서
False를 반환하려면 활성 matcher 전체에 대해 불가능함을 증명해야 한다.
특수문자가 없다는 이유로 Fuzzy를 생략하거나, 원문 Exact가 없다는 이유로 우회 검사를 생략하지 않는다.
증명이 어려운 경로는 기존 matcher를 사용한다.

## 6. 대안과 우선순위

| 방안 | 장점 | 비용·한계 | 판단 |
| --- | --- | --- | --- |
| 기본값을 strict로 축소 | 즉시 호출 비용 일부 감소 | 초성 탐지 감소, 정규화 비용은 남음 | 근본 개선책으로 채택하지 않음 |
| Fuzzy 제외 구성 제공 | 현재 API로 가능, 실측 비용 감소 | 일부 오타 미탐 | 단기 선택지 |
| 일반 입력 정규화 개선 + bool 경로 | 핵심 기능을 유지하며 반복 비용 절감 | Unicode·Whitelist·예외 동등성 검증 필요 | 우선 구현 |
| 입력별 안전한 단계 생략 | 고급 기능의 불필요한 실행 감소 | 잘못된 조건은 미탐·Whitelist 회귀 | 증명된 조건부터 확대 |
| C/Rust 등 native 구현 | Python 순회 비용을 줄일 가능성 | 빌드·3 OS wheel·유지보수·배포 비용 | 앞 단계가 목표를 못 맞출 때 별도 검토 |
| 텍스트 결과 캐시 | 중복 요청이 많으면 비용 감소 가능 | 원문 보관·메모리·동시성·사전별 key 정책 필요 | 실제 중복률 확인 전 보류 |

탐지율을 조용히 줄이는 기본값 변경보다, 사용자가 비용을 명시적으로 선택하는 구성을 제공한다.
엔진 인스턴스를 요청마다 새로 만들지 않는 사용 예시도 유지한다.

## 7. 제안 성능 목표와 수용 조건

아래 수치는 **초기 실험 목표**다. 아직 달성한 결과나 서비스 SLA가 아니다.
같은 장비·Python·입력·반복 수에서 baseline과 Korcen을 다시 실행해 판정한다.

### 절대 목표를 세우기 전에 확인한 하한

초안의 절대 목표 두 개(`0.020ms`, `2ms`)는 이 문서의 진단만으로는 도달할 수 없다.
정규화 비용을 **0으로 가정한** 이론상 하한을 직접 측정해 확인했다.

| 입력 | balanced `check()` | 그중 `normalize_text` | 정규화를 0으로 둔 하한 |
| --- | ---: | ---: | ---: |
| 짧은 욕설 | 0.0280ms | 0.0062ms (22.1%) | **0.0218ms** |
| 4,096자 일반 한글 | 4.8633ms | 3.1183ms (64.1%) | **1.75ms** |

짧은 욕설의 하한 0.0218ms는 초안 목표 0.020ms보다 크다. 즉 A(정규화)만으로는 도달할 수
없고, B(bool 경로)가 matcher 디스패치와 `Match`·`CheckResult` 생성 비용까지 줄여야 한다.
3절이 이미 "결과 객체 생성 최적화만으로 해소한다고 약속할 수 없다"고 적었으므로, 두
진술을 함께 두면 절대치 목표의 근거가 없다.

4,096자에서는 글자별 span을 유지하는 한 tuple 생성 0.4351ms가 바닥이므로, 정규화가
span 생성만 남는 최선의 경우에도 `check()`는 약 2.18ms다. 초안 목표 2ms를 맞추려면
5A의 span 표현 변경이 **필수**다. 이 측정은 프로파일러 없이 수행했고 위 4절·2절과
장비·실행 방식이 다르므로 이 절 안에서만 비교한다.

따라서 절대 지연 목표를 삭제하고 baseline 상대 감소로 바꾼다. 절대치는 span 표현
변경 범위를 확정하고 P1 실측이 나온 뒤에 다시 세운다.

| 대상 | 초기 목표 |
| --- | --- |
| balanced bool·짧은 직접 욕설 | baseline 대비 30% 이상 감소. 절대치 목표는 P1 실측 뒤 재설정 |
| balanced bool·짧은 정상 | baseline 대비 10% 초과 퇴행 없음 |
| balanced bool·4,096자 일반 입력 | baseline 대비 50% 이상 감소. 2ms 이하는 span 표현 변경을 포함한 경우에만 목표로 삼는다 |
| 전체 `check()` | 결과 완전 동일, 대표 workload에서 10% 초과 퇴행 없음 |
| Fuzzy 제외 고급 구성 | baseline 대비 비용 감소와 잃는 탐지 건수를 함께 기록 |
| 복잡한 Unicode·사용자 사전·최악 입력 | 올바른 fallback, 공개 길이·계산량 제한 유지, 새 초선형 경로 없음 |

Korcen 상대 배수도 기록하지만 더 적은 탐지를 수행한 결과를 같은 기능의 가속으로 보고하지 않는다.
목표를 못 맞추면 최대 2회의 최적화 사이클 뒤 병목 근거로 범위를 재결정한다.

정확성 gate는 고정 회귀·Unicode·Alias 겹침·Whitelist 변환·최대 길이와 결정적 생성 입력에 대한
`contains`/`check` 차등 검증이다. 성공/실패뿐 아니라 예외 타입과 공개 예외 필드도 비교한다.
변경 전후 `check`의 match 내용·순서를 비교하며 시간 필드 `elapsed_ms`는 동일성 비교에서 제외한다.
모든 기존 품질 검사와 branch 측정 활성화 상태의 총 coverage 90% 기준도 유지한다.

기존 2,763건 tuning의 확정 원문은 현재 체크아웃에서 찾지 못했다. 다만 원문과 label을
가진 확정 케이스 830건은 체크아웃에 있으므로 차등 검증의 baseline으로 바로 쓸 수 있다.

| 파일 | 케이스 |
| --- | ---: |
| `evaluation/corpus/tuning/curated-policy-slices-v1.json` | 250 |
| `evaluation/corpus/tuning/curated-positive-slice-buffer-v1.json` | 480 |
| `evaluation/corpus/tuning/curated-hard-negative-buffer-v1.json` | 100 |

각 케이스는 `text`, `label`, `expected_matches`를 갖고 있어 `contains`/`check` 차등 검증과
match 내용·순서 비교에 그대로 사용할 수 있다. P0의 baseline 고정에 이 830건을 포함한다.
830건은 빠른 경로의 공개 회귀 검증에는 충분하지만, **profile 기본값을 바꾸는 정확도 근거**를
대신할 수는 없다. 그 판단에는 2,763건 tuning과 보호 hidden이 필요하다.

## 8. 실행 묶음과 출시 반영

| 순서 | 산출물·담당 영역 | 완료 기준 |
| --- | --- | --- |
| P0: 비교 기준 고정 | benchmarks·기존 비교 스크립트·API 계약 | 입력 길이/분포/위치별 baseline, 보존할 동작과 예외 목록 |
| P1: 정규화 빠른 경로 | normalizer·Unicode/성능 테스트 | 일반 입력 개선, 복잡한 입력 fallback와 span 동등성 |
| P2: bool 경로 | engine·matcher·contains 계약/테스트 | 우선 strict/balanced 동등성, 목표 지연, 예외 보존 |
| P3: 고급 구성 정리 | README recipe·측정 보고서 | Fuzzy 제외의 비용/미탐 명시, 기본값 변경 없음 |
| P4: 후보 검증 | 전체 품질 gate·release 문서 | 새 commit/artifact의 검사 결과와 남은 제한 기록 |

1명의 유지관리자를 가정한 초기 추정은 P0~P3에 약 5~10 작업일이다. Unicode mapping 변경과
사용자 사전 경계 테스트 결과에 따라 달라지며, 보호 평가·3 OS CI·배포 승인의 대기 시간은 제외했다.

### 출시 범위 선택 — 미결정

2026-09-09 기준으로 [출시 계획](release-0.1.0-execution-plan.md)의 새 후보
`e6576925cfce46ed0c23356d4610be3a5b0cebbe`는 3 OS·재현성 CI와 artifact 검증을 이미
통과했고 hidden 평가만 남아 있다. 따라서 이 제안을 `0.1.0`에 넣는다는 것은 준비를 마쳐가는
후보를 폐기하고 또 다른 후보를 잡는다는 뜻이다. 두 선택지를 나란히 둔다.

| 선택 | 내용 | 대가 |
| --- | --- | --- |
| A. `0.1.0`에 포함 | 새 RC를 고정하기 전에 P0~P3을 반영 | 현재 후보 폐기, P0~P3 5~10 작업일 + hidden 재평가, authoritative artifact 2026-09-22 만료 전 완료 불확실 |
| B. `0.2.0`으로 연기 | 현재 후보로 `0.1.0`을 마무리하고 성능 작업은 다음 판에서 진행 | 첫 공개판이 현재 지연 특성으로 나감. 4절 Fuzzy 제외 구성은 기존 API로 이미 제공 가능 |

이 문서는 어느 쪽도 결정하지 않는다. B를 고르면 4절 구성만 README recipe로 안내하고
P0~P4는 `0.1.0` 이후로 넘긴다. A를 고르면 새 후보의 품질·hidden·TestPyPI 근거를 다시
마련하고 이전 RC의 평가를 재사용하지 않는다.
목표 미달로 native 구현까지 필요한 경우에는 그 추가 범위를 별도로 판단해 출시가 계속 늘어지지 않게 한다.

## 9. 이번 기획에서 실행한 것

- 현재 `contains`, 정규화, Whitelist union, Fuzzy 계산량 경로와 기존 계약·테스트 검토.
- 8개 profile/workload 조합의 cProfile 조사 및 원문 없는 함수별 통계 보존.
- 동일한 공개 진단 52건에 대한 Fuzzy 제외 비교와 4개 workload의 3라운드 시간 측정.
- 변환 Whitelist와 Fuzzy 예외의 조기 종료 반례 각각 재현.
- 새 문서·JSON의 링크, 집계와 기준 commit 확인.

2026-09-09 검토에서 추가로 실행한 것:

- 4절 Fuzzy 제외 집계를 원본 JSON과 대조. `changed_diagnostic_ids`는 `obfuscation-11`

프로파일러 비중은 우선순위 근거이고, 목표 달성은 추후 프로파일러 없는 실제 benchmark로 판단한다.
