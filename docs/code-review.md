# Koguard 코드 리뷰 기준

리뷰는 요약보다 finding을 먼저 작성한다. 실제 결함과 회귀 가능성을 우선하며, 단순한 스타일
선호는 자동 포매터나 기존 규칙을 위반하지 않는 한 finding으로 만들지 않는다.

## 우선순위

- P0: 데이터 손실, 임의 코드 실행, 비밀정보 노출처럼 즉시 배포를 막아야 하는 문제
- P1: 일반 입력에서 잘못된 탐지 결과, 공개 API 파손, 심각한 성능·보안 회귀
- P2: 특정 경계값에서 발생하는 오동작, 누락된 검증, 유지보수 위험
- P3: 영향은 작지만 명확히 수정할 가치가 있는 문제

## 정확성

- `detected`가 항상 `bool(matches)`와 같은가?
- 매치는 원문 위치, 긴 구간, matcher 우선순위 기준으로 결정적으로 정렬되는가?
- 겹치는 후보를 제거해도 서로 떨어진 유효 매치는 유지되는가?
- `start`와 `end`가 원문 기준 반열림 구간 `[start, end)`인가?
- Unicode 정규화와 제거 문자 때문에 span이 어긋나지 않는가?
- Whitelist가 겹치는 후보만 제외하고 다른 매치를 보존하는가?
- 빈 문자열, 잘못된 타입, 최대 길이 입력의 정책이 일관적인가?

## 보안과 개인정보

- 입력 길이 또는 후보 수 제한을 우회해 CPU·메모리를 과도하게 사용할 수 있는가?
- 사용자 입력이나 탐지된 표현이 로그, 예외, 임시 파일에 불필요하게 남는가?
- 사전 경로와 파일 인코딩 오류가 안전하고 명확하게 처리되는가?
- 외부 데이터·모델·코드가 출처 및 라이선스 검증 없이 배포물에 포함되는가?
- core 동작에 예상하지 못한 네트워크 호출이 추가되는가?

## 설계와 호환성

- 공개 타입, 예외, 필드 의미가 예고 없이 바뀌는가?
- Engine과 Dictionary가 생성 후 안전하게 공유 가능한가?
- 선택 의존성이 core 설치에 강제로 포함되는가?
- 테스트만 통과시키는 특례가 일반 규칙을 깨뜨리는가?

## 테스트

- 변경 동작을 실패로 재현하고 성공을 검증하는 테스트가 있는가?
- 정상 문장과 오탐 방지 사례가 함께 있는가?
- corpus 기대값이 변경되었다면 이유가 문서화되었는가?
- branch coverage 90% 기준과 정적 검사가 유지되는가?

finding에는 파일과 좁은 줄 범위, 발생 조건, 실제 영향을 포함한다. finding이 없으면 그 사실과
검증하지 못한 범위를 분명히 쓴다.
